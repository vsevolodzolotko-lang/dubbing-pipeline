# E2E-тест: archive snapshot settings carry-over

Перевірка фіксу `ARCHIVE_SNAPSHOT_SETTINGS_CARRYOVER` (DECISIONS 2026-06-16): чи містить
архівний `sheet_snapshot_{...}` налаштування **того рану, що архівується**, а не ті, що
оператор уже вписав під наступний.

**Статус:** деплой + смоук-тест пройдено 2026-06-16 (ноди зелені, `_run_settings_carryover.json`
створюється). Повну перевірку коректності (нижче) ще НЕ ганяли — цей документ її описує.

## Чому потрібно 2 рани

Carry-over споживається на архіві **наступного** рану. Снепшот, який архівує рану X,
робиться на старті рану X+1. Тому:
- 1-й ран після деплою (`run_1`) лише **сіє** carry-over; снепшот, що він робить (архів `run_0`),
  ще з живими налаштуваннями — це bootstrap, ігноруємо.
- 2-й ран (`run_2`) архівує `run_1` і **застосовує** carry-перенесення → саме його снепшот
  (названий по `run_1`) перевіряємо.

Снепшот робиться на **початку** рану (до W1), тож чекати повну локалізацію не треба —
після архіву (~1 хв) можна тиснути 🛑 **Stop**, щоб не платити за синтез.

## Якщо НЕ працює — діагностика

- n8n → **Executions** → запуск `run_2` → перевір 9 carry-over-нод (між `Copy Sheet Snapshot`
  і `Plan Subfolders`). Усі best-effort (`onError: continueRegularOutput`), тож червона нода не
  валить ран, але означає, що снепшот лишився з живими налаштуваннями:
  - `Find Carryover` повернув порожньо → carry-over файл не знайдено (перевір ім'я/теку = `drive_archive_folder_id`).
  - `Read Carryover Content` 404 → файл є, але не читається; на 1-му рані це норма (bootstrap).
  - `Patch Snapshot Settings` не 200 → перевір, що URL цілить у **копію** (`Copy Sheet Snapshot.id`), не в живу таблицю.
  - Вирази `(( … )[0] || {}).id` / `specifyBody: json` / `uploadType=media` — якщо движок виразів старий, дивись логи ноди.
